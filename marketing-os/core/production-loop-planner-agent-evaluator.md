# Производственный цикл: planner → agent → evaluator + contract

**Статус:** draft (тестируем)
**Тип:** метод производства артефактов с контролем качества
**Где применяем:** сборка лендингов, лидген-воронок, КП, контента — везде, где «сам сделал → сам проверил → соврал что готово» убивает качество
**Владелец:** Володя
**Дата создания:** 2026-06-10
**Первый пилот:** hero-секция посадочной под плёнку (Левша) → см. дашборд детейлинга

---

## Зачем

Качество долгой автономной работы держится не на «модель умная», а на архитектуре процесса. Источник — выступление Anthropic про агентов, которые работают часами. Ключевой рычаг: **критерии готовности фиксируются ДО сборки и согласуются между двумя ролями**, а не пишутся исполнителем самому себе.

У Володи часть этого уже была изобретена самостоятельно: независимое тестирование + DoD (definition of done). Этот документ доводит схему до целого цикла.

---

## Модель (как у Anthropic)

```text
planner → agent → evaluator
```

Маленькая продуктовая команда из агентов. У каждого своя роль, свой контекст, своя зона ответственности.

### 1. Planner — верхний план и спринты
Получает короткий запрос и превращает его в структуру работы:
- что собираем;
- какие большие части нужны;
- в какой последовательности идти;
- какие спринты должны получиться.

**Важно:** planner НЕ расписывает всю техническую реализацию заранее. Подробный план на 200 шагов с ошибкой в начале погонит ошибку каскадом через часы работы. Planner держит уровень продукта и спринтов; технические решения остаются ближе к моменту реализации.

### 2. Agent — сборка следующего спринта
Берёт следующий спринт и собирает фичу. **Но перед началом договаривается с evaluator, что именно считается готовым результатом.** Это главный механизм всей системы.

### 3. Contract — договорённость о «готово»
- Agent: «я соберу такую фичу, проверять надо так».
- Evaluator: «добавь такой сценарий, такой edge case, такое состояние интерфейса, такую проверку».
- Обмениваются markdown-файлами, уточняют критерии, пока не сходятся.

Contract — **список конкретных проверяемых утверждений.** Дальше evaluator проверяет не расплывчатый исходный запрос, а этот contract.

Пример. Запрос: «сделай retro game maker».
Contract:
- можно создать новый проект;
- есть sprite editor;
- есть play mode;
- сохраняется состояние;
- canvas работает корректно;
- основные сценарии кликаются в браузере.

У Anthropic для одного приложения вышло **27 contract criteria**.

> Расплывчатые критерии → расплывчатая критика → agent получает «ну как-то не очень» и не понимает, что чинить. Конкретные критерии → точная проблема.

### 4. Evaluator — жёсткая проверка через браузер
Отдельный агент-критик. Открывает приложение через Playwright, кликает по интерфейсу, делает скриншоты, проверяет сценарии, пишет критику, отдаёт agent. Отдельный контекст + отдельная инструкция = проще настроить быть жёстким. **Agent собирает. Evaluator атакует результат.** Так появляется давление на качество.

### 5. Финальный цикл
```text
1. planner разбивает задачу на спринты
2. agent берёт следующий спринт
3. agent и evaluator согласуют contract
4. agent строит
5. evaluator проверяет через браузер
6. agent чинит
7. цикл повторяется
```

С новыми моделями схему можно упрощать: agent может два часа спокойно собирать, потом evaluator прогоняет проверку.

## Перевод на наши примитивы

| Роль Anthropic | Наш примитив | Статус |
|---|---|---|
| **Planner** | разбивка лендинга на секции/спринты (hero → оффер → доказательства → CTA) по RDB | роль не выделена |
| **Agent** | `/copywriter` + сборка секции | ✅ есть |
| **Contract (DoD)** | `contract.md`: проверяемые пункты из RDB, Hormozi, уровней Шварца | концепт есть, оформляем как файл |
| **Evaluator** | отдельный subagent + Playwright (`.tools/snapshot.py`, `section-shot.py`, `hero-shot.py`) | инструменты есть, роль не выделена |

### Где схема сильная и где слабая
- **Сильная — лендинги/лидген.** Есть кликабельная поверхность → браузерный evaluator работает в полную силу.
- **Слабая — чистый текст (посты, КП, лонгриды).** Клиента нет на экране → evaluator превращается в **rubric-критика**: проверяет черновик против чек-листа (RDB выдержан? оффер по Hormozi? анти-сегмент отсечён? один JTBD, не каша?). Это `/code-review`, но по маркетинг-рубрике. Полезно, но это «полцикла» — давления браузера нет.

### Что уже было у Володи
**DoD = их contract.** Независимое тестирование = их evaluator. Разница ровно одна: Anthropic фиксирует contract ДО сборки и согласует между двумя ролями, а не пишет исполнитель сам себе.

## Что нужно, чтобы собрать самому

- subagents для отдельных ролей (planner / agent / evaluator);
- Playwright / Chrome MCP для проверки интерфейса;
- skills / rubrics для критериев качества;
- auto mode / permissions для долгой автономной работы;
- **contract-файлы** для договорённости о «готово» до начала реализации.

## Пилот: hero-секция плёнки (Левша)

Не воспроизводить всё сразу. Один заход на реальном артефакте:

1. **Planner** режет посадочную под плёнку на спринты-секции.
2. До сборки пишем `contract.md`: 10–15 проверяемых пунктов на hero. Не «сделай красиво», а:
   - виден оффер с конкретным результатом за N;
   - есть низкострессовый шаг (расчёт по фото);
   - мобильная версия не режет CTA;
   - закрыто возражение про цену плёнки в первом экране;
   - и т.д.
3. `/copywriter` собирает.
4. **Evaluator-subagent** открывает desktop + mobile через Playwright, скриншотит, бьёт по contract, пишет критику.
5. Чиним по конкретным пунктам, повторяем.

Результат пилота — не новый большой документ, а отработанный цикл на одной секции + вывод: где схема даёт качество, где трение.

Связанный артефакт лендинга: film-funnel, текущий лендинг: film-landing/index.html.
