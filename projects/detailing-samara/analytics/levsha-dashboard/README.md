# Левша — локальная аналитика

Локальный контур для еженедельного объединения ручных выгрузок Битрикс24, 1С и рекламных кабинетов.

## Еженедельное обновление

1. Выгрузить из Б24 **все сделки, изменённые за неделю**, без фильтра «только закрытые» и с телефонами связанных контактов.
2. Положить файл сделок в `inbox/b24/`.
3. Выгрузить из Б24 **все лиды, изменённые за неделю**, с телефонами, стадией, датой изменения стадии и причиной обращения; положить файл в `inbox/leads/`.
4. Выгрузить продажи 1С за ту же календарную неделю и положить CSV или XLSX в `inbox/1c/`.
5. Положить детальную выгрузку рекламы в `inbox/ads/`.
6. Дважды нажать `Обновить аналитику.bat` (Windows) или `Обновить аналитику.command` (macOS).

После успешной обработки файлы перемещаются в `archive/`, база обновляется, а в браузере открывается `dashboard/index.html`. Файл с ошибкой попадает в `errors/`, рабочая база при этом не меняется.

## Следующий этап

1. Повысить полноту связки заказ-нарядов 1С с Б24: сейчас однозначно сопоставлены 164 из 236 заказов.
2. Подключить получение сделок Б24 через входящий вебхук и обновлять записи по времени изменения.
3. После сверки Б24 проверить получение рекламы по API Яндекс Директа и VK.
4. Проверить, какие UTM и рекламные ID сохраняются в сделках Б24. Без этой связки детализация ниже канала будет показывать только кабинетные метрики, но не SQL, продажи и выручку.
5. После подтверждения качества добавить к группам и объявлениям сделки, продажи и выручку по UTM/рекламным ID.

До завершения первой сверки Б24 ↔ 1С рекламные API не подключаются: ручные выгрузки остаются основным источником.

## Имена файлов

Рекомендуемый формат:

```text
B24_2026-08-10_2026-08-16.csv
LEADS_2026-08-10_2026-08-16.csv
1C_2026-08-10_2026-08-16.csv
YANDEX_DETAILED_2026-08-10_2026-08-16.csv
```

Повторная загрузка исправленного файла 1С или рекламы за тот же период заменяет этот период и не создаёт дубли. Б24 обновляется по ID сделки; в показателе «Сделок по Б24» считается количество строк с датой создания.

## Правила расчёта

- календарная неделя: понедельник–воскресенье;
- лиды обновляются по `ID`, поэтому повторная выгрузка изменившихся лидов обновляет стадию без дублей;
- квал — фактическая стадия лида `Качественный лид`;
- лид связывается со сделкой Б24 по моменту конвертации: дата создания сделки должна совпасть с датой изменения стадии лида в пределах 10 секунд; телефон и название используются как дополнительные признаки;
- новые: `Повторная сделка = N`;
- повторные: `Повторная сделка = Y`;
- «Успех + в работе»: успешная стадия, `В работе`, а также стадии записи из `config/stage_map.json`;
- «Записан, не сделан»: стадии записи, которые ещё не стали успешной сделкой;
- нулевые заказы 1С сохраняются в сыром слое, но не участвуют в количестве продаж, среднем чеке, атрибуции и рекламной экономике;
- из выручки 1С исключаются только строки с явным признаком коррекции;
- до загрузки 1С вместо выручки показывается только справочная «Сумма Б24», CAC, ROAS и ROI не рассчитываются;
- после загрузки 1С CAC, ROAS и ROI рассчитываются отдельно по каналам, где есть расход и связанная фактическая продажа;
- заявки в таблице каналов считаются как строки сделок Б24 соответствующего источника;
- для VK используются два источника показателя: расход из рекламного кабинета и заявки из Б24 с источником `VK`; кабинетные «Результаты» и попытки отдельно выделять сообщения, формы или звонки не используются;
- SQL в таблице каналов считается как расход рекламного кабинета / заявки Б24 этого источника;
- расход VK хранится в исходном виде без НДС, а для показателей дашборда к нему добавляется НДС 22%;
- расход Яндекс Директа импортируется и показывается в исходном виде с НДС;
- дневной расход Авито вводится как фактически указанная сумма без дополнительного начисления НДС;
- сравнение каналов, SQL, CAC, ROAS и ROI строится по расчётному расходу каждого источника;
- в эффективности каналов можно выбрать все, только новые или только повторные сделки; рекламный расход при этом остаётся общим расходом канала за выбранный период;
- канал с рекламными данными раскрывается до кампаний: расход с НДС, показы, клики, CTR, CPC, конверсии и CPA кабинета; показатели Б24 и 1С на кампании не распределяются без UTM;
- для Яндекс Директа лидом в кабинетной статистике считаются только звонки с коллтрекинга и заявки на сайте;
- детальная выгрузка Яндекс Директа сохраняет кампанию, группу, объявление, ключевую фразу и поисковый запрос;
- компактная кампанийная выгрузка Яндекса больше не используется: детальная выгрузка полностью заменяет её за тот же период;
- канал Яндекса в дашборде раскрывается по иерархии `кампания → группа → объявление`; на каждом уровне показываются расход с НДС, показы, клики, CTR, CPC, лиды и CPA;
- топ‑10 ключевых фраз строится за выбранный период только по фразам с лидами: сначала по количеству лидов, при равенстве — по меньшему CPA; автотаргетинг и строки без ключевой фразы в рейтинг не входят;
- поисковые запросы сохраняются только в `data/levsha.sqlite3` для будущей оптимизации рекламы и не публикуются в `dashboard/data.js`;
- рекламные агрегаты считаются по дневной детализации; служебные строки «Итого» в импорт не попадают;
- стадии записи и `В работе` участвуют в CR, но не считаются фактическими продажами или выручкой;
- бухгалтерская прибыль не рассчитывается; ROI использует оценочную маржу 30% из `config/analytics_rules.json`;
- сделки и CR относятся к дате создания Б24, фактическая выручка — к дате реализации 1С;
- выручка 1С сначала связывается с Б24 по номеру заказ-наряда; если номера нет или он неоднозначен — по единственному совпадению нормализованного телефона в окне до 45 дней между созданием сделки и реализацией;
- если одному телефону соответствуют несколько сделок, автоматическая привязка разрешается только к успешной сделке при уникальном совпадении даты успеха/записи, суммы либо ближайшей даты успеха в пределах трёх дней;
- если у заказа 1С несколько разных телефонов или после дополнительных правил остаётся несколько кандидатов, автоматическая привязка не выполняется;
- ручная связка из `config/manual_matches.csv` имеет приоритет над автоматическими правилами;
- для будущих периодов номер заказ-наряда должен быть заполнен в Б24 до перевода сделки в `Сделка успешна`.

## Воронка по направлениям и сравнение периодов

Анализ вынесен на отдельную страницу `dashboard/funnels.html`; между ней и основным обзором есть навигация. Обе страницы используют один `dashboard/data.js`, поэтому отдельного обновления не требуется.

Направление берётся из поля лида Б24 `Причина обращения`. Для каждого направления сохраняется дневная агрегация по дате создания лида и текущей стадии: лиды, квалифицированные обращения, созданные сделки и три взаимоисключающих исхода сделки. `Успешные` — стадии `Сделка успешна` и `Автомобиль выдан клиенту`; `Неуспешные` — остальные закрытые сделки; все незакрытые сделки показываются отдельно как `Открытые`. В ячейке успешных дополнительно показывается сумма поля Б24 `Сумма` только этих успешных сделок. Она подписана как `Сумма Б24` и не подменяет фактическую выручку 1С. Правила исходов хранятся в `config/deal_outcome_rules.json`.

Показатель `Квал` теперь фактический: считается текущая стадия `Качественный лид`, правило хранится в `config/lead_stage_map.json`. Связь лида со сделкой строится по совпадению времени конвертации в пределах 10 секунд, затем уточняется телефоном и названием. Если выгрузки сделок нет за часть истории лидов, дашборд ограничивает воронку первым днём доступных сделок, чтобы не показывать искусственный ноль на последнем шаге.

Основной фильтр задаёт период A: последние 7 дней, текущий месяц, весь сопоставимый период или произвольные даты. Рядом доступен срез `Все / Только новые / Только повторные`. В блоке направлений можно включить период B и выбрать предыдущий период той же длины, прошлый календарный месяц или ручной диапазон.

На странице доступен независимый фильтр платного источника `Все / Яндекс Директ / VK / Авито`. Источник берётся из исходного лида после применения `config/source_rules.json`, поэтому фильтр одновременно перестраивает направления, стадии, исходы сделок и средний чек 1С. Звонки без UTM и другого подтверждённого признака источника остаются в канале `Звонок` и не приписываются платной рекламе.

Воронка визуально располагается слева направо: `Лиды → Лид→квал → Квал → Квал→сделка → Создана сделка`, после чего разветвляется на `Успешные / Открытые / Неуспешные`. В каждой ветке показываются количество и доля от созданных сделок; отдельно считается сквозная конверсия `Лид→успешная сделка`. Для каждого направления повторяется тот же порядок колонок. При включённом сравнении значение периода A находится непосредственно над периодом B в одной ячейке: для количества показывается относительное изменение в процентах, для конверсий — изменение в процентных пунктах. Таблица стадий лидов использует ту же вертикальную схему A/B/Δ.

В каждой строке направления также показывается `Средний чек 1С` и количество заказов, на котором он рассчитан. Формула: фактическая выручка однозначно связанных заказов 1С / количество этих заказов. Показатель является когортным: заказ относится к периоду по дате создания исходного лида, как и остальные этапы этой страницы. Если связанных заказов нет, вместо нуля выводится `—`.

Исторические периоды являются когортами по дате создания, а не снимками состояния на прошлую дату: если старая сделка меняет статус и повторно попадает в выгрузку Б24, её результат обновится и в прошлом периоде.

## Ручные соответствия 1С ↔ Б24

Спорные заказы можно один раз привязать в `config/manual_matches.csv`:

```text
Номер заказ-наряда 1С;Дата реализации 1С;ID сделки Б24;Комментарий
1023;2026-08-05;12345;проверено вручную
```

Дата нужна, если номер заказ-наряда может повторяться. После сохранения файла достаточно снова нажать `Обновить аналитику.command`. Несуществующий ID сделки или конфликтующие строки остановят обновление, чтобы выручка не ушла в неправильный канал.

## Правила распределения источников

Все названия и приоритеты каналов хранятся в `config/source_rules.json`. Правила применяются сверху вниз и автоматически пересчитываются для всех уже загруженных сделок Б24 при каждом обновлении.

Приоритет полей: `UTM Source` → `ДКТ: Источник` → `Источник` → `Канал обращения` → `Точка входа обращения`. Канал определяется вместе с `UTM Medium` или `ДКТ: Канал`.

- звонок с коллтрекинга `yandex + cpc` → `Яндекс Директ`;
- `yandex + organic` → `Яндекс Органика`;
- `google + organic` → `Google Органика`;
- `(direct) + (none)` → `Прямой трафик`;
- `ya_maps` → `Яндекс Карты`;
- `ya_biz` → `Яндекс Бизнес`;
- звонок на подтверждённый выделенный номер `…15226` → `Авито`;
- звонок без UTM и без источника ДКТ остаётся в канале `Звонок`.

Коллтрекинг — это тип обращения, а не отдельный рекламный канал. Если UTM заполнены, звонок относится к источнику из UTM.
Подтверждённые статические номера коллтрекинга имеют приоритет над полем `Источник = Звонок`; их соответствия каналам также хранятся в `config/source_rules.json`.

## Квалификация лида

`config/qualification_rules.json` считает **технический прокси по текущей стадии Б24**, а не полную квалификацию. Каноническое определение — пять подтверждённых критериев и приоритет A/B в [стандарте квалификации](../../sales/lead-qualification-criteria-by-service-2026-07-31.md).

Пока обязательные признаки не записываются в CRM и не прошли выборочную сверку, показатель дашборда можно использовать для внутренней динамики обработанных целевых обращений, но нельзя выдавать за точное число квалифицированных лидов или использовать в расчёте агентской оплаты за результат.

## CAC, ROAS и ROI

Метрики считаются отдельно по каждому каналу, когда одновременно есть рекламный расход и связанная с этим каналом фактическая продажа 1С. Общая доля сопоставления 1С ↔ Б24 остаётся показателем качества данных, но больше не скрывает метрики каналов целиком.

- `CAC` = расход с НДС / связанные заказы 1С;
- `ROAS` = связанная фактическая выручка 1С / расход с НДС;
- `ROI 30%` = (связанная выручка 1С × 30% − расход с НДС) / расход с НДС.

Если расхода или связанной продажи нет, показывается `—`, а не ноль. Маржа для ROI хранится в `config/analytics_rules.json`; сейчас принята оценка 30%. В срезах `Только новые` и `Только повторные` полный расход канала сравнивается только с результатом выбранного сегмента, поэтому эти значения являются консервативными и не означают распределение рекламного бюджета между сегментами.

## Форматы источников

Б24 уже поддерживается в формате текущей CSV-выгрузки. Для сопоставления по клиенту в экспорт нужно включать поля `Контакт: Рабочий телефон`, `Контакт: Мобильный телефон` и остальные доступные телефоны контакта. Номера приводятся к последним 10 цифрам и хранятся только в SQLite; в `dashboard/data.js` они не попадают. Для 1С и рекламы лежат стартовые шаблоны в `templates/`. После получения реальных выгрузок сопоставление колонок уточняется в `config/import_mappings.json` без изменения базы и дашборда.

### Стандартная выгрузка 1С

Импортёр поддерживает иерархический XLSX-отчёт `Продажи по заказам`: покупатель → заказ-наряд → услуги, с дневными колонками количества и выручки. Датой реализации считается дата дневной колонки, а не дата создания в названии заказ-наряда.

Точные повторы одного заказ-наряда за одну дату с одинаковой выручкой удаляются. Повтор с разными значениями останавливает импорт. Короткие номера 1С (`1023`, `ЛЭ-2443`, `ЭЛ-2289`) сопоставляются с полными номерами Б24 (`00ЛВ-001023`, `ЛЭЛВ-002443`, `ЭЛЛВ-002289`). Нулевые заказы сохраняются в SQLite для проверки исходной выгрузки, но исключаются из аналитических расчётов; строки с явным признаком коррекции также не участвуют в расчётах.

Историческая выгрузка клиентов хранится в слое данных как справочный источник. В текущие показатели она не включается: в ней почти нет телефонов, а номера заказов неоднозначно повторяются между периодами. В дальнейшем её можно использовать для отдельного исследования LTV и повторности по клиентам.

### Стандартная выгрузка Яндекс Директа

Для Яндекса используется один детальный CSV за нужный период. Он должен содержать дату, ID и название кампании, ID и название группы, ID объявления, ключевую фразу, поисковый запрос, показы, клики, расход и конверсии. Лидами в отчёте остаются только звонки с коллтрекинга и заявки на сайте.

Компактную кампанийную выгрузку отдельно загружать не нужно. Импортёр отклонит её, если в файле нет уровня группы, объявления, ключевой фразы и поискового запроса.

## Два слоя

- данные: `data/levsha.sqlite3`, исходные файлы и правила в `config/`;
- визуализация: статические файлы `dashboard/`; `index.html` — общий обзор, `funnels.html` — направления и сравнение периодов.

На хостинг в дальнейшем достаточно выгрузить содержимое `dashboard/`. В него попадают только агрегаты, без имён и телефонов клиентов.
